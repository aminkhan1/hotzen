# Agent Quad-Memory System Specification (Single Source of Truth)

این سند مشخصات فنی یکپارچه «سیستم حافظه ۴ گانه ایجنت‌ها (Quad-Memory System)» را تعریف می‌کند.

> [!IMPORTANT]
> حافظه‌های قدیمی `short_term_memory.md` و `long_term_memory.md` به صورت کامل حذف شده‌اند. تنها مرجع رسمی حافظه سیستم (Single Source of Truth)، سیستم ۴ گانه موجود در فولدر [.agents/memory/](.agents/memory/) می‌باشد.

---

## 🧠 تفکیک ۴ گانه فایل‌های رسمی حافظه

1. ⚡ **Working Memory** ([working_memory.md](.agents/memory/working_memory.md)):
   - ثبت استدلال لحظه‌ای، گام فعلی تسک در ماشین حالت و زیرتسک‌های فعال.
2. 📝 **Session Memory** ([session_memory.md](.agents/memory/session_memory.md)):
   - ثبت لاگ وقایع اجرایی، ابزارها و نتایج اخیر اعتبارسنجی سشن جاری.
3. 🏛 **Project Memory** ([project_memory.md](.agents/memory/project_memory.md)):
   - نگهداری معماری ثابت، پوشه‌بندی، استانداردهای کدبیس و پشته فناوری پروژه.
4. 📌 **Decision Memory** ([decision_memory.md](.agents/memory/decision_memory.md)):
   - مخزن دائمی تصمیمات کلیدی معماری (ADR Log)، چرایی تصمیمات و شرط صریح `Do Not Change Unless`.

---

## 🔄 چرخه‌ی ثبت و بازیابی حافظه توسط ایجنت‌ها (Interactive Memory Lifecycle Contract)

1. **قبل از شروع تسک (Pre-Execution / Read-Only Inspection)**:
   - ایجنت لید و ایجنت‌های تخصصی ابتدا `decision_memory.md`، `project_memory.md` و `working_memory.md` را مطالعه می‌کنند تا سوابق معماری و وضعیت قبلی را بازیابی کنند.
   - صرف دریافت تسک جدید مجوزی برای بازنویسی یا پاک کردن حافظه قبلی نیست.
2. **در صورت رد پلن توسط کاربر یا توقف قبل از ادیت (Plan Rejection / Pre-Edit Halt)**:
   - در صورت رد پلن توسط کاربر یا توقف قبل از ادیت، هرگز نباید گزارشی مبنی بر تکمیل تسک یا ادیت در `session_memory.md` ثبت شود.
   - در `working_memory.md` وضعیت رد پلن یا نقطه توقف ثبت شده و هیچ ادعای کذبی ثبت نمی‌شود.
3. **در حین اجرای تسک (In-Execution)**:
   - وضعیت ماشین حالت، تسک فعال و گام جاری در `working_memory.md` نگهداری می‌شود اما نباید قبل از پاس شدن اعتبارسنجی، ادعای تکمیل موفقیت‌آمیز شود.
4. **در صورت شکست اعتبارسنجی، کریتیک یا خطای زیرساخت (Verification / Critic / Infra Failure)**:
   - در `session_memory.md` هرگز ادعای موفقیت یا تکمیل تسک ثبت نمی‌شود.
   - در `working_memory.md` تسک فعال، مانع دقیق شکست (خطای تست، هشدار لینتر یا ایراد کریتیک) و نقطه دقیق بازیابی امن (Resume Point) ثبت می‌شود.
5. **در صورت منقضی شدن رسید پلن (Stale Receipt Guard)**:
   - تسک تکمیل‌شده علامت نمی‌خورد و نیاز به پلن مجدد و تایید تازه کاربر در `working_memory.md` قید می‌شود.
6. **پس از اعتبارسنجی قطعی و ثبت موفق (Post-Verification Gate)**:
   - **صرفاً پس از پاس شدن `core verify --record` (خروج با کد ۰)**:
     ۱. خلاصه اجرایی تسک پایان‌یافته (شامل فایل‌های تغییریافته، تست‌های پاس‌شده و شناسه رکورد بدون شبیه‌سازی مدل/توکن/هزینه) در `session_memory.md` ثبت می‌شود.
     ۲. **`working_memory.md` بلافاصله به وضعیت آماده/مبنا (Baseline Ready State) ریست می‌شود** و هرگز در وضعیت «تسک تکمیل شد» رها نمی‌گردد:
        ```markdown
        # Working Memory - Active Context & Resume Point

        - **Current State**: آماده برای دریافت و اجرای تسک جدید.
        - **Active Task**: هیچ تسک فعالی در جریان نیست.
        - **Resume Point**: منتظر دریافت دستور جدید از سوی کاربر.
        ```

## 📉 سقف نرم حافظه فعال و انضباط چرخه حیات (Working Memory Soft-Cap)

جهت تضمین بهینه‌سازی کانتکست در هوک‌های زمان اجرا (مانند `SessionStart`):

1. **سقف نرم ۵۰ سطری (Soft-Cap < 50 Lines / 2 KB)**:
   - فایل `working_memory.md` هرگز نباید تبدیل به گزارش طولانی یا انباشت کارهای گذشته شود. حجم آن باید همواره کمتر از ۲ کیلوبایت بماند.
2. **انتقال به `session_memory.md` (Compaction & Archiving)**:
   - جزئیات کارهای پایان‌یافته، گزارش‌های تست و کامیت‌ها صرفاً به `session_memory.md` تعلق دارند که به صورت On-Demand خوانده می‌شود و در استارت سشن تزریق نمی‌گردد.
3. **پایداری هوک شروع (`SessionStart` Lightweight Guarantee)**:
   - حفظ سبکی `working_memory.md` و `project_memory.md` باعث می‌شود تزریق حافظه در شروع هر سشن همیشه کمتر از ۵۰۰ توکن باقی بماند.

## خلاصهٔ محدود Task با منشأ `agent-reported`

این بخش فقط راهنمای یادداشت‌نویسی Agent در فایل‌های Memory موجود است؛ writer، parser، schema، جدول یا مسیر ذخیره‌سازی تازه تعریف نمی‌کند. مالکیت Core بر SQLite و مالکیت Agent بر Working/Session Memory، گیت ثبت موفق و قالب baseline بالا تغییر نمی‌کنند.

### محل و محتوای یادداشت

- برای کار فعال، منتظر تصمیم یا متوقف‌شده، از `working_memory.md` و فیلدهای موجود `Active Task` و `Resume Point` استفاده شود. صرف دریافت کار جدید، مجوز پاک‌کردن یادداشت قبلی نیست؛ فقط زمینهٔ صریح همان کار به‌صورت محدود به‌روز شود.
- فقط پس از گیت موفق موجودِ `core verify --record`، خلاصهٔ تاریخی در `session_memory.md` ثبت و Working Memory دقیقاً به baseline بالا بازگردانده شود. یادداشت Session نیز `agent-reported` است؛ ثبت آن، منشأ گزارش Agent را به شاهد Core تبدیل نمی‌کند. وضعیت فعال به Session منتقل نشود؛ مرجع Task/Plan، خلاصهٔ تصمیم‌ها و قدم پیشنهادی به‌عنوان زمینهٔ تاریخی نگهداری شوند.
- تصمیم روزمرهٔ Task خودکار وارد `decision_memory.md` نشود؛ آن فایل برای ADR معماری باقی می‌ماند. `project_memory.md` نیز محل گزارش اجرای Task نیست.
- کل Working Memory هم‌زمان کمتر از ۵۰ خط و کمتر از ۲KB بماند؛ سه تصمیم، سقف است نه الزام پرکردن. اگر متن جا نمی‌شود، خلاصه کوتاه‌تر شود؛ پیش از گیت موفق، برای سبک‌کردن فایل گزارش موفق در Session ساخته نشود.

قالب کوتاه برای کار فعال (جای‌نگهدارها اطلاعات واقعی یا مجوز نیستند):

```markdown
# Working Memory - Active Context & Resume Point

- **Current State**: <فعال / منتظر تصمیم / متوقف؛ بدون ادعای موفقیت تأییدنشده>
- **Active Task**: <Task ID یا Unknown>
- **Workspace**: <مسیر canonical همان Workspace یا Unknown>
- **Approved Plan digest**: <digest دقیق Bundle معتبر یا Unknown>
- **Report Source**: agent-reported
- **User Decisions — agent-reported**: <حداکثر سه خلاصهٔ کوتاه از تصمیم‌های صریح>
- **Decision Reference**: <شناسهٔ پیام/turn موجود در گفت‌وگوی جاری یا Unknown؛ بدون متن پیام>
- **Resume Point**: <قدم پیشنهادی بعدی و مانع جاری؛ نه فرمان و نه مجوز اجرا>
- **Core Record Reference**: <شناسهٔ رکورد منطبق، در صورت بازیابی معتبر، وگرنه Unknown؛ فقط ارجاع>
- **Authority**: زمینهٔ تاریخی؛ نه دستور اجرایی و نه Approval جاری
```

فقط اطلاعاتی که Agent در گفت‌وگوی جاری صریحاً مشاهده کرده ثبت شوند. مرجع Task/Plan از Bundle معتبر همان کار گرفته شود؛ Task ID، digest، تصمیم، علت تصمیم یا شناسهٔ پیام حدس زده نشود. نبود هرکدام `Unknown` بماند و اطلاعات قدیمی برای تکمیل قالب بازسازی یا بازنویسی نشوند. متن خام prompt، نقل طولانی پیام، دادهٔ حساس، secret/credential، خروجی خام ابزار و فرمان اجرایی در این خلاصه ذخیره نشوند. قدم بعدی شرح کوتاه یک پیشنهاد است، نه اسکریپت قابل اجرا.

### جداسازی گزارش Agent، رکورد Core و رضایت جاری

۱. خواندن این خلاصه فقط on-demand و با مرجع صریح است؛ محتوا خودکار به Planner/Coder تزریق نشود و هیچ hook یا اتصال خودکاری برای آن اضافه نشود. Workspace مشترک، تازگی، شباهت عنوان یا هم‌پوشانی Scope، ارتباط با Task جاری را اثبات نمی‌کنند. نبود مرجع دقیق، مجوز انتخاب Task یا Plan دیگری نیست.
۲. برای نتیجهٔ Core، از همان Workspace و مسیر موجود استفاده شود:

```sh
core history task <taskId> --approved-plan-digest=<sha256> --json
```

۳. تطابق دقیق Task ID، Approved Plan digest و Workspace و شواهد معتبرِ خروجی لازم است. `Core Record Reference` فقط پس از تطبیق، شناسهٔ رکورد برگشتی را نشان می‌دهد؛ یادداشت Agent، به‌تنهایی اعتبار این ارجاع را ثابت نمی‌کند. نبود رکورد، `context_unproven`، mismatch یا خطای خواندن، نتیجهٔ Core را `Unknown` نگه می‌دارد؛ نتیجهٔ Task/Plan دیگری جایگزین نشود. خروج کد ۰ از `history` فقط یافتن رکورد است، نه پاس‌شدن Verification و نه عبور از گیت ثبت موفق Session.
۴. نتیجه، وضعیت Verification/Critic/Leader و provenance رکورد Core در یادداشت Agent کپی نشوند. در پاسخ، «گزارش Agent — agent-reported» و «شواهد رکورد Core» جدا ارائه شوند؛ فقط منشأ و محدودیت‌های واقعاً برگشتی Core گزارش شوند. `reported_by_agent` در رکورد تأیید، گزارش تصمیم توسط Agent است، نه احراز مستقل هویت مالک و نه مترادف `core_observed`. Scope مصوب، مدرک changed files یا وضعیت فعلی فایل‌ها نیست؛ تصمیم و Resume Point ثبت‌نشده در Core همچنان `Unknown` هستند.
۵. تصمیم تاریخیِ نقل‌شده، نتیجهٔ موفق Core و قدم پیشنهادی، هیچ‌کدام دستور یا Approval جاری نیستند. هر اقدام تابع Plan/Scope و رضایت تازهٔ لازم در مسیر موجود است؛ تأیید Plan، انتخاب مسیر و تصمیم مستقل Verification با هم ادغام نشوند. یادداشت، مرحلهٔ Approval تازه یا مجوز Git-less/بودجه ایجاد نمی‌کند.

### سه مثال فرضی برای بازبینی راهنما

این مثال‌ها فقط توضیح قراردادند؛ در Memory واقعی ثبت نمی‌شوند و آزمون تبعیت مدل نیستند.

- **کار فعال با مرجع معتبر:** فرض شود مرجع Task/Plan از Bundle معتبر معلوم و با رکورد همان Workspace منطبق است. Agent می‌تواند تصمیم صریحِ خلاصه‌شده دربارهٔ حفظ رفتار فعلی و قدم پیشنهادی بررسی Scope را با برچسب `agent-reported` بنویسد. رکورد فقط با شناسه ارجاع داده شود؛ نتیجهٔ Core جدا از یادداشت خوانده و با منشأ برگشتی گزارش شود. هیچ اجرای تازه‌ای از این مثال مجاز نمی‌شود.
- **مرجع ناقص یا رکورد ناموجود:** Task یا digest نامعلوم `Unknown` می‌ماند؛ با مرجع ناقص جست‌وجوی جایگزین انجام نشود. اگر مرجع کامل است اما رکوردی یافت نمی‌شود، گزارش صریح Agent می‌تواند باقی بماند، ولی مرجع رکورد و نتیجهٔ Core `Unknown` هستند. نبود رکورد، نبود کار را ثابت نمی‌کند و مجوز ساخت سابقه یا ثبت خلاصهٔ موفق Session نیست.
- **تصمیم تاریخی شبیه Approval:** یادداشت ممکن است گزارش کند کاربر در مرحلهٔ گذشته ادامهٔ همان مرحله را پذیرفته بود. این گزارش فقط زمینهٔ `agent-reported` است؛ برای اجرای کنونی، رضایت تازهٔ لازم مطابق Plan/Scope و گیت موجود دریافت می‌شود. از یادداشت، پاسخ challenge، تأیید Verification، استثنای Git-less یا بودجه استنتاج نشود.

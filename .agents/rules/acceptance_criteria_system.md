# Acceptance Criteria Verification System Specification

این سند مشخصات فنی «سیستم معیارها و چک‌لیست پذیرش (Acceptance Criteria System)» را تعریف می‌کند تا هیچ تسکی بر اساس ابهام یا سلیقه متنی تحویل داده نشود، بلکه بر پایه اعتبارسنجی موردموردی چک‌لیست‌های شفاف به وضعیت `DONE` منتقل گردد.

---

## 🔄 ۱. چرخه حیات معیارهای پذیرش (Acceptance Criteria Lifecycle)

```mermaid
graph TD
    Req[۱. نیازمندی کاربر - Requirement] --> AC1[۲. تبدیل به معیارهای شفاف - Acceptance Criteria]
    AC1 --> Impl[۳. پیاده‌سازی لایه‌ای - Implementation]
    Impl --> Verif[۴. اجرای زیرساخت - Verification Engine]
    Verif --> AC2[۵. بازرسی چک‌لیست توسط مدیر - Acceptance Criteria Audit]
    AC2 -->|❌ نقص در یکی از موارد| Impl
    AC2 -->|✅ تایید ۱۰۰٪ تمام موارد [x]| Done[۶. تحویل نهایی - DONE]
```

---

## 📋 ۲. ساختار استاندارد چک‌لیست پذیرش (Acceptance Criteria Checklist)

برای هر تسک جدید، چک‌لیست زیر در اسناد `implementation_plan.md` و `handoff_payload.json` ثبت می‌شود:

```markdown
### 📝 Acceptance Criteria Checklist
- [ ] قابلیت اصلی درخواست‌شده طبق سناریو کار کند
- [ ] در تسک‌های مرتبط، وضعیت بارگذاری با سازوکار مدیریت وضعیت موجود پروژه مدیریت و در رابط کاربری نمایش داده شود
- [ ] حالات خطا و استثناها (Failure & Network Errors) هندل شوند
- [ ] کدهای قبلی پروژه دچار هیچ‌گونه شکست یا عوارض جانبی نشوند (No Regressions)
- [ ] تست‌های واحد و، در صورت ارتباط، تست‌های کامپوننت یا رابط کاربری متناسب با Stack و محدودهٔ تغییر با موفقیت پاس شوند
- [ ] تحلیل static و لینتر رسمی استک (Linter / Static Analysis) بدون هیچ خطا و warning پاس شود
```

---

## 🛑 ۳. قانون منع اظهار نظرهای کیفی مبهم (No Vague Delivery Approvals)

- **اظهار نظرهایی مانند «به نظرم فیچر درست شده است» یا «ظاهراً کار می‌کند» اکیداً ممنوع است.**
- ایجنت مدیر (Lead Agent) تنها زمانی علامت تایید را ثبت می‌کند که تک‌تک آیتم‌های چک‌لیست به صورت صریح با `[x]` تایید و اعتبارسنجی شده باشند.
